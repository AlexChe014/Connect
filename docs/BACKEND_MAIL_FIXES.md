# Бэкенд: баги почты (кодировка, заголовки, push, отправка не с того ящика)

Клиент (Flutter) проверен — раздел [«Почта»](../lib/screens/mail_inbox_screen.dart) сам
по себе рабочий (список, папки, вложения, ответ/пересылка, mark read/unread всё
починены на клиенте). Ниже — 4 проблемы, для которых фикс нужен на сервере
(Laravel/PHP), с точным описанием, что видно с клиента, и где смотреть.

## 1. Отправка письма уходит не с того ящика

**Симптом:** пользователь открывает конкретный почтовый ящик (например, второй
подключённый аккаунт), нажимает «Написать», отправляет письмо — но письмо
физически уходит с другого (видимо, «дефолтного») SMTP-аккаунта.

**Почему так:** `POST /mail/smtp/send` (используется для нового письма и для
ответа/пересылки с вложениями) **не принимает и не отправляет никакого
идентификатора ящика** — только `to`, `subject`, `body_text`, `attachments[]`.
Сравните с `/mail/smtp/set/{connectionId}` — этот эндпоинт выставляет ящик
«по умолчанию» глобально для пользователя, и, судя по поведению, именно этот
дефолт и используется сервером при `smtp/send`, независимо от того, какой
ящик реально открыт в клиенте.

Для сравнения: `/mail/smtp/reply/{messageId}` и `/mail/smtp/forward/{messageId}`
ведут себя правильно — сервер сам резолвит аккаунт-отправитель по ящику
исходного письма (это в клиенте используется намеренно, см. комментарий в
[compose_mail_screen.dart](../lib/screens/compose_mail_screen.dart)).

**Нужно:**
- Добавить `connection_id` (или `account_id`) как параметр `POST /mail/smtp/send`.
- Отправлять письмо именно с этого SMTP-аккаунта, а не с дефолтного.
- Как только эндпоинт примет параметр — сообщите, клиент передаст
  `connection.id` того ящика, в котором открыт компоузер (сейчас это поле уже
  доступно в форме, просто некуда его положить).

## 2. Кодировка писем (мусор вместо текста)

**Симптом:** часть писем (судя по всему, не в UTF-8 — например, из старых
рассылок или писем с указанием `charset=windows-1251` / `koi8-r`) приходит на
клиент с «кракозябрами» в теле и/или теме.

**Где смотреть:** место разбора IMAP-сообщения на сервере — декодирование
`Content-Transfer-Encoding` (base64 / quoted-printable) и последующая
перекодировка из заявленного в письме `charset` в UTF-8 **до** того, как текст
попадает в JSON-ответ `/mail/get/message/{connection}/{id}` (и в превью списка
`/mail/get/folder/...` / `/mail/get/service/...`). Если письмо в не-UTF-8
кодировке отдаётся как есть (без `mb_convert_encoding`/`iconv`), клиент как раз
и получит текущую картину.

## 3. Текст «No headers found» вместо письма

**Симптом:** у некоторых писем в теле (иногда в теме) буквально видна строка
`No headers found` — похоже на текст исключения из библиотеки парсинга MIME
(это типичное сообщение об ошибке `webklex/php-imap`, если он используется),
которое по ошибке попадает в поле `body`/`subject` ответа вместо того, чтобы
быть обработанным как ошибка.

**Нужно:** найти, где на сервере вызывается парсер заголовков письма, обернуть
в try/catch отдельно от парсинга тела, и при неудаче не подставлять текст
исключения в контент письма — вернуть `body: null` (клиент для этого случая
уже показывает «Текст письма отсутствует», см.
[mail_body_content.dart](../lib/widgets/mail_body_content.dart)) либо
попытаться дособрать сообщение из сырых заголовков другим способом.

## 4. Push-уведомления о новой почте не приходят

**Симптом:** клиент готов принимать и показывать push о новом письме, но они
не приходят вообще (в отличие от чата, где такая же проблема уже была
исправлена — см. `project_chat_push_notifications_broken` в памяти: там
`broadcast()` вызывался до `DB::afterCommit()`, и push иногда уходил раньше
записи в БД / вообще не уходил при определённых условиях гонки).

**Контракт, который уже ждёт клиент** (см.
[push_notification_service.dart:378](../lib/services/push_notification_service.dart#L378)):

```json
{
  "type": "mail",
  "connection_id": "<id ящика>",
  "message_id": "<id письма>"
}
```

FCM data-only пуш (без блока `notification`, как и для звонков/чата — иначе
может не разбудить навигацию из фона).

**Нужно:** найти, где (в фоновой IMAP-синхронизации / job'е, который подтягивает
новые письма) должен диспатчиться push, и проверить:
- вызывается ли отправка push вообще при появлении нового письма;
- если да — не «гонка» ли это с коммитом транзакции, как было в чате
  (`afterCommit` vs прямой `broadcast()`/`send()`).

## Чеклист

- [ ] `POST /mail/smtp/send` принимает `connection_id` и шлёт именно с этого ящика
- [ ] Тело/тема писем в не-UTF-8 кодировке декодируются в UTF-8 на сервере
- [ ] Ошибка парсинга заголовков не подставляется как текст письма («No headers found»)
- [ ] Push `type=mail` уходит при получении нового письма (data-only, `connection_id` + `message_id`)
