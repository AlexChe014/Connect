# Бэкенд: баги почты (кодировка, заголовки, push, отправка не с того ящика)

Клиент (Flutter) проверен — раздел [«Почта»](../lib/screens/mail_inbox_screen.dart) сам
по себе рабочий (список, папки, вложения, ответ/пересылка, mark read/unread всё
починены на клиенте). Ниже — 4 проблемы, для которых фикс нужен на сервере
(Laravel/PHP), с точным описанием, что видно с клиента, и где смотреть.

## 1. Отправка письма уходит не с того ящика

**Симптом:** пользователь открывает конкретный почтовый ящик (например, второй
подключённый аккаунт), нажимает «Написать», отправляет письмо — но письмо
физически уходит с другого (видимо, «дефолтного») SMTP-аккаунта.

**Почему так:** `POST /mail/smtp/send` (используется для нового письма и для
ответа/пересылки с вложениями) **не принимает и не отправляет никакого
идентификатора ящика** — только `to`, `subject`, `body_text`, `attachments[]`.
Сравните с `/mail/smtp/set/{connectionId}` — этот эндпоинт выставляет ящик
«по умолчанию» глобально для пользователя, и, судя по поведению, именно этот
дефолт и используется сервером при `smtp/send`, независимо от того, какой
ящик реально открыт в клиенте.

Для сравнения: `/mail/smtp/reply/{messageId}` и `/mail/smtp/forward/{messageId}`
ведут себя правильно — сервер сам резолвит аккаунт-отправитель по ящику
исходного письма (это в клиенте используется намеренно, см. комментарий в
[compose_mail_screen.dart](../lib/screens/compose_mail_screen.dart)).

**Нужно:**
- Добавить `connection_id` (или `account_id`) как параметр `POST /mail/smtp/send`.
- Отправлять письмо именно с этого SMTP-аккаунта, а не с дефолтного.
- Как только эндпоинт примет параметр — сообщите, клиент передаст
  `connection.id` того ящика, в котором открыт компоузер (сейчас это поле уже
  доступно в форме, просто некуда его положить).

## 2. Кодировка писем (мусор вместо текста)

**Симптом:** часть писем (судя по всему, не в UTF-8 — например, из старых
рассылок или писем с указанием `charset=windows-1251` / `koi8-r`) приходит на
клиент с «кракозябрами» в теле и/или теме.

**Где смотреть:** место разбора IMAP-сообщения на сервере — декодирование
`Content-Transfer-Encoding` (base64 / quoted-printable) и последующая
перекодировка из заявленного в письме `charset` в UTF-8 **до** того, как текст
попадает в JSON-ответ `/mail/get/message/{connection}/{id}` (и в превью списка
`/mail/get/folder/...` / `/mail/get/service/...`). Если письмо в не-UTF-8
кодировке отдаётся как есть (без `mb_convert_encoding`/`iconv`), клиент как раз
и получит текущую картину.

## 3. Текст «No headers found» вместо письма

**Симптом:** у некоторых писем в теле (иногда в теме) буквально видна строка
`No headers found` — похоже на текст исключения из библиотеки парсинга MIME
(это типичное сообщение об ошибке `webklex/php-imap`, если он используется),
которое по ошибке попадает в поле `body`/`subject` ответа вместо того, чтобы
быть обработанным как ошибка.

**Нужно:** найти, где на сервере вызывается парсер заголовков письма, обернуть
в try/catch отдельно от парсинга тела, и при неудаче не подставлять текст
исключения в контент письма — вернуть `body: null` (клиент для этого случая
уже показывает «Текст письма отсутствует», см.
[mail_body_content.dart](../lib/widgets/mail_body_content.dart)) либо
попытаться дособрать сообщение из сырых заголовков другим способом.

**Временный клиентский фильтр (2026-09-24):** пока бэкенд не пофикшен,
[mail_message.dart](../lib/models/mail/mail_message.dart) распознаёт
буквальные строки `No headers found` / `No header found` в `subject`/`body`
и трактует их как отсутствие темы/тела (`(без темы)` /
«Текст письма отсутствует» вместо самой строки-исключения). Это не решает
проблему — сервер всё ещё выполняет лишний парсинг и может прислать другой
текст исключения, который клиент не узнает; нужен настоящий фикс по пункту
выше.

## 4. Push-уведомления о новой почте не приходят

**Симптом:** клиент готов принимать и показывать push о новом письме, но они
не приходят вообще (в отличие от чата, где такая же проблема уже была
исправлена — см. `project_chat_push_notifications_broken` в памяти: там
`broadcast()` вызывался до `DB::afterCommit()`, и push иногда уходил раньше
записи в БД / вообще не уходил при определённых условиях гонки).

**Контракт, который уже ждёт клиент** (см.
[push_notification_service.dart:378](../lib/services/push_notification_service.dart#L378)):

```json
{
  "type": "mail",
  "connection_id": "<id ящика>",
  "message_id": "<id письма>"
}
```

FCM data-only пуш (без блока `notification`, как и для звонков/чата — иначе
может не разбудить навигацию из фона).

**Нужно:** найти, где (в фоновой IMAP-синхронизации / job'е, который подтягивает
новые письма) должен диспатчиться push, и проверить:
- вызывается ли отправка push вообще при появлении нового письма;
- если да — не «гонка» ли это с коммитом транзакции, как было в чате
  (`afterCommit` vs прямой `broadcast()`/`send()`).

## 5. Локальная копия писем не синхронизируется с реальным состоянием ящика

**Симптомы (четыре разных, но с одним корнем):**
- письмо, удалённое через веб-версию почты, продолжает показываться в списке
  в приложении;
- **и наоборот:** письмо, удалённое в приложении, продолжает быть видно в
  веб-версии/другом клиенте — см. отдельно пункт 6 ниже, там же вопрос, не
  «фейковое» ли это удаление (только в зеркале, без реального IMAP-delete);
- письмо, прочитанное в вебе (или ранее в приложении), в приложении всё равно
  подсвечено синей точкой как непрочитанное;
- **отправленные** письма (папка «Отправленные») тоже показаны как
  непрочитанные — хотя по стандарту IMAP письма в Sent всегда имеют флаг
  `\Seen`.

**Почему это бэкенд, не клиент:** список писем (`GET /mail/get/folder/...`,
`GET /mail/get/service/...`, `GET /mail/fetch/{connection}`) отдаётся не с
IMAP напрямую, а из локальной зеркальной таблицы на сервере. Клиент ничего не
досчитывает и не переопределяет:
- точка «непрочитано» — это буквально `!is_read` из ответа API
  ([mail_inbox_screen.dart:884](../lib/screens/mail_inbox_screen.dart#L884)),
  `is_read`/`seen` берётся из JSON как есть
  ([mail_message.dart:171](../lib/models/mail/mail_message.dart#L171));
  никакого спецкейса «в Sent всегда read» на клиенте нет;
- `GET /mail/fetch/{connection}` («забрать письма с сервера») по описанию и
  ответу (`data: Email[]`) похож на «добавить новые», и непонятно, вычищает
  ли он из зеркала письма, пропавшие на IMAP-сервере.

**Нужно проверить на сервере:**
- job синхронизации при первой вставке письма в зеркальную таблицу должен
  читать реальный флаг `\Seen` с IMAP (а не проставлять дефолт `is_read =
  false` для всех новых строк, включая Sent);
- при повторной синхронизации (в т.ч. по `/mail/fetch/{connection}`) флаг
  `is_read` уже существующих в зеркале писем должен обновляться, если он
  изменился на сервере (например, письмо прочитали через веб);
- синхронизация должна замечать письма, исчезнувшие на IMAP-сервере
  (удалённые не через приложение), и удалять/помечать их как удалённые в
  зеркальной таблице — иначе они висят в приложении бессрочно.

## 6. Удаление письма в приложении не удаляет его на самом ящике

**Симптом:** пользователь удаляет письмо в приложении — оно пропадает из
списка в приложении, но продолжает быть видно в веб-версии почты (то есть
реально на IMAP-сервере). При этом клиент перед удалением показывает
предупреждение «Письмо будет удалено без возможности восстановления»
([mail_message_screen.dart:137-139](../lib/screens/mail_message_screen.dart#L137-L139)) —
то есть UX обещает необратимое удаление, а по факту (судя по симптому)
письмо не удаляется, а самое большее — скрывается в зеркальной таблице.

**Что вызывает клиент:** простой `GET /mail/delete/{connectionId}/{messageId}`
([mail_repository.dart:438-445](../lib/repositories/mail_repository.dart#L438-L445),
роут в [mail_routes.dart:68-69](../lib/config/routes/mail_routes.dart#L68-L69)),
без каких-либо параметров вроде `expunge`/`permanent`. Есть также пакетный
вариант `GET /mail/delete/few/{connectionId}`. По самой сигнатуре запроса
нельзя понять, что реально происходит на сервере.

**Нужно проверить на сервере:** выполняет ли обработчик этого роута настоящее
IMAP-удаление (`STORE \Deleted` + `EXPUNGE` на реальном ящике), или только
удаляет/помечает строку в локальной зеркальной таблице. Если только
зеркало — это не просто баг синхронизации, а функциональный баг: письмо
физически никогда не удаляется с сервера, хотя приложение утверждает
обратное.

## 7. Долгая загрузка детального экрана письма

**Симптом:** открытие письма (особенно непрочитанного) ощутимо медленнее,
чем список.

**Со стороны клиента:** [mail_message_screen.dart `_loadMessage()`](../lib/screens/mail_message_screen.dart#L52-L130)
при открытии письма делает один запрос
`GET /mail/get/message/{connectionId}/{messageId}`, и если письмо ещё не
прочитано — **последовательно**, вторым запросом (не параллельно),
`POST /mail/mark/read/{connectionId}/{messageId}`
([mail_message_screen.dart:83-106](../lib/screens/mail_message_screen.dart#L83-L106)).
Никакого лишнего клиентского перечитывания папки/тяжёлого синхронного
парсинга при открытии нет, вложения грузятся только по тапу пользователя —
то есть на клиенте это максимум «два последовательных round-trip вместо
одного» для непрочитанных писем, а не системная причина.

**Нужно проверить на сервере:**
- сколько реально занимает сам `GET /mail/get/message/...` — похоже, что он
  делает живой запрос к IMAP-серверу синхронно на каждое открытие письма
  (а не отдаёт из зеркальной таблицы, как список), это и есть вероятный
  источник задержки;
- можно ли отдавать тело письма сразу из зеркала (если оно там уже есть после
  синхронизации), обновляя его на фоне, а не блокировать открытие письма
  живым IMAP-запросом.
- как быстрый выигрыш на клиенте: можно сделать `mark/read` фоновым (не
  дожидаться его перед показом письма) — это уберёт один
  round-trip из критического пути, но не решит основную задержку, если она
  на стороне `get/message`.

## Чеклист

- [ ] `POST /mail/smtp/send` принимает `connection_id` и шлёт именно с этого ящика
- [ ] Тело/тема писем в не-UTF-8 кодировке декодируются в UTF-8 на сервере
- [ ] Ошибка парсинга заголовков не подставляется как текст письма («No headers found»)
- [ ] Push `type=mail` уходит при получении нового письма (data-only, `connection_id` + `message_id`)
- [ ] Синхронизация читает реальный `\Seen` с IMAP при вставке письма в зеркало (в т.ч. для Sent)
- [ ] Синхронизация обновляет `is_read` существующих писем, если флаг изменился на сервере
- [ ] Синхронизация удаляет из зеркала письма, пропавшие на IMAP-сервере
- [ ] `GET /mail/delete/{connectionId}/{messageId}` реально удаляет письмо на IMAP-сервере, а не только в зеркале
- [ ] `GET /mail/get/message/{connectionId}/{messageId}` не блокирует открытие письма живым IMAP-запросом (отдаёт из зеркала / кэширует)
