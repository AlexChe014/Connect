# Бэкенд: баги почты (кодировка, заголовки, push, отправка не с того ящика)

## Проверка клиента 2026-09-28

Исправлены смешивание всех папок со «Входящими», скрытие вложенных черновиков,
подмена ошибочно загруженной папки общим списком и выделение отправленных как
новых. Отображаются реальные папки с отдельными серверными ID, включая архив.
Статус `is_read` имеет приоритет над старым `seen`; ответы-подтверждения без
объекта письма поддерживаются для прочтения, ответа и пересылки.

Открытый список и счётчик непрочитанных перечитывают серверное зеркало по
таймеру (60 секунд), при возврате в приложение и при push. Ручное обновление
запускает `/mail/fetch`; сбой синхронизации показывается пользователю.
Для Android добавлено отображение data-only почтовых push в фоне и обработка
перехода из локального уведомления при холодном запуске.

Перед новой SMTP-отправкой клиент выбирает текущий ящик через `/mail/smtp/set`.
Это меняет серверный ящик по умолчанию. Гонка между двумя устройствами остаётся
возможной: нужна атомарная отправка с `connection_id`, описанная ниже.

В согласованиях добавлены счётчики по каждому сервису по списку документов.
Завершённые статусы исключаются; записи старого формата без статуса считаются
элементами очереди 1С. При недоступности сервиса/необходимости кода показывается
индикатор ошибки проверки. Для точного счёта при других значениях статусов или
ограниченном списке серверу нужен отдельный `pending_count` по текущему пользователю.

Проверки API выполняются на подставных ответах. Доставка реальных писем,
пушей и двусторонняя IMAP-синхронизация не подтверждены: серверного кода и
тестового устройства/ящика в этой проверке нет. Ниже сохранены серверные
проблемы и требования, требующие проверки на рабочем окружении.

Дополнительно проверить на сервере:
- IMAP LIST/SPECIAL-USE возвращает черновики (включая вложенные), а синхронизация
  сохраняет письма без получателя, темы и полных заголовков.
- Изменения `\\Seen` синхронизируются в обе стороны, включая уже существующие письма.
- Статус прочтения получателем исходящего письма — отдельная функция MDN;
  текущий `is_read` описывает состояние письма в собственном ящике и не является
  подтверждением прочтения адресатом.

## 1. Отправка письма уходит не с того ящика

**Симптом:** пользователь открывает конкретный почтовый ящик (например, второй
подключённый аккаунт), нажимает «Написать», отправляет письмо — но письмо
физически уходит с другого (видимо, «дефолтного») SMTP-аккаунта.

**Почему так:** `POST /mail/smtp/send` (используется для нового письма и для
ответа/пересылки с вложениями) **не принимает и не отправляет никакого
идентификатора ящика** — только `to`, `subject`, `body_text`, `attachments[]`.
Сравните с `/mail/smtp/set/{connectionId}` — этот эндпоинт выставляет ящик
«по умолчанию» глобально для пользователя, и, судя по поведению, именно этот
дефолт и используется сервером при `smtp/send`, независимо от того, какой
ящик реально открыт в клиенте.

Для сравнения: `/mail/smtp/reply/{messageId}` и `/mail/smtp/forward/{messageId}`
ведут себя правильно — сервер сам резолвит аккаунт-отправитель по ящику
исходного письма (это в клиенте используется намеренно, см. комментарий в
[compose_mail_screen.dart](../lib/screens/compose_mail_screen.dart)).

**Нужно:**
- Добавить `connection_id` (или `account_id`) как параметр `POST /mail/smtp/send`.
- Отправлять письмо именно с этого SMTP-аккаунта, а не с дефолтного.
- Сейчас клиент сначала вызывает `/mail/smtp/set/{connectionId}`. После поддержки
  `connection_id` заменить эти два запроса одной атомарной отправкой.
- (2026-10-21) Чтобы отправка со второго ящика не меняла молча ящик по
  умолчанию, клиент теперь перед отправкой читает `/mail/smtp/get/sendable`,
  а после отправки возвращает прежний `is_default`. Это 2–4 запроса вместо
  одного и всё ещё не атомарно — с `connection_id` в `smtp/send` всё это
  можно убрать (`MailRepository.sendMail`).

## 2. Кодировка писем (мусор вместо текста)

**Симптом:** часть писем (судя по всему, не в UTF-8 — например, из старых
рассылок или писем с указанием `charset=windows-1251` / `koi8-r`) приходит на
клиент с «кракозябрами» в теле и/или теме.

**Где смотреть:** место разбора IMAP-сообщения на сервере — декодирование
`Content-Transfer-Encoding` (base64 / quoted-printable) и последующая
перекодировка из заявленного в письме `charset` в UTF-8 **до** того, как текст
попадает в JSON-ответ `/mail/get/message/{connection}/{id}` (и в превью списка
`/mail/get/folder/...` / `/mail/get/service/...`). Если письмо в не-UTF-8
кодировке отдаётся как есть (без `mb_convert_encoding`/`iconv`), клиент как раз
и получит текущую картину.

## 3. Текст «No headers found» вместо письма

**Симптом:** у некоторых писем в теле (иногда в теме) буквально видна строка
`No headers found` — похоже на текст исключения из библиотеки парсинга MIME
(это типичное сообщение об ошибке `webklex/php-imap`, если он используется),
которое по ошибке попадает в поле `body`/`subject` ответа вместо того, чтобы
быть обработанным как ошибка.

**Нужно:** найти, где на сервере вызывается парсер заголовков письма, обернуть
в try/catch отдельно от парсинга тела, и при неудаче не подставлять текст
исключения в контент письма — вернуть `body: null` (клиент для этого случая
уже показывает «Текст письма отсутствует», см.
[mail_body_content.dart](../lib/widgets/mail_body_content.dart)) либо
попытаться дособрать сообщение из сырых заголовков другим способом.

**Временный клиентский фильтр (2026-09-24):** пока бэкенд не пофикшен,
[mail_message.dart](../lib/models/mail/mail_message.dart) распознаёт
буквальные строки `No headers found` / `No header found` в `subject`/`body`
и трактует их как отсутствие темы/тела (`(без темы)` /
«Текст письма отсутствует» вместо самой строки-исключения). Это не решает
проблему — сервер всё ещё выполняет лишний парсинг и может прислать другой
текст исключения, который клиент не узнает; нужен настоящий фикс по пункту
выше.

## 4. Push-уведомления о новой почте не приходят

**Симптом:** клиент готов принимать и показывать push о новом письме, но они
не приходят вообще (в отличие от чата, где такая же проблема уже была
исправлена — см. `project_chat_push_notifications_broken` в памяти: там
`broadcast()` вызывался до `DB::afterCommit()`, и push иногда уходил раньше
записи в БД / вообще не уходил при определённых условиях гонки).

**Контракт, который уже ждёт клиент** (см.
[push_notification_service.dart:378](../lib/services/push_notification_service.dart#L378)):

```json
{
  "type": "mail",
  "connection_id": "<id ящика>",
  "message_id": "<id письма>"
}
```

Для фонового показа предпочтителен FCM `notification` + `data` (с APNs alert
для iOS); навигация читает `data` после тапа. Android также обрабатывает
data-only локальным уведомлением. Нельзя полагаться на доставку silent/data-only
в завершённое приложение iOS. Проверить foreground/background/cold start на устройстве.

**Нужно:** найти, где (в фоновой IMAP-синхронизации / job'е, который подтягивает
новые письма) должен диспатчиться push, и проверить:
- вызывается ли отправка push вообще при появлении нового письма;
- если да — не «гонка» ли это с коммитом транзакции, как было в чате
  (`afterCommit` vs прямой `broadcast()`/`send()`).

## 5. Локальная копия писем не синхронизируется с реальным состоянием ящика

**Симптомы (четыре разных, но с одним корнем):**
- письмо, удалённое через веб-версию почты, продолжает показываться в списке
  в приложении;
- **и наоборот:** письмо, удалённое в приложении, продолжает быть видно в
  веб-версии/другом клиенте — см. отдельно пункт 6 ниже, там же вопрос, не
  «фейковое» ли это удаление (только в зеркале, без реального IMAP-delete);
- письмо, прочитанное в вебе (или ранее в приложении), в приложении всё равно
  подсвечено синей точкой как непрочитанное;
- **отправленные** письма (папка «Отправленные») тоже показаны как
  непрочитанные — хотя по стандарту IMAP письма в Sent всегда имеют флаг
  `\Seen`.

**Почему это бэкенд, не клиент:** список писем (`GET /mail/get/folder/...`,
`GET /mail/get/service/...`, `GET /mail/fetch/{connection}`) отдаётся не с
IMAP напрямую, а из локальной зеркальной таблицы на сервере. Клиент ничего не
досчитывает и не переопределяет:
- точка «непрочитано» — это буквально `!is_read` из ответа API
  ([mail_inbox_screen.dart:884](../lib/screens/mail_inbox_screen.dart#L884)),
  `is_read`/`seen` берётся из JSON как есть
  ([mail_message.dart:171](../lib/models/mail/mail_message.dart#L171));
  никакого спецкейса «в Sent всегда read» на клиенте нет;
- `GET /mail/fetch/{connection}` («забрать письма с сервера») по описанию и
  ответу (`data: Email[]`) похож на «добавить новые», и непонятно, вычищает
  ли он из зеркала письма, пропавшие на IMAP-сервере.

**Нужно проверить на сервере:**
- job синхронизации при первой вставке письма в зеркальную таблицу должен
  читать реальный флаг `\Seen` с IMAP (а не проставлять дефолт `is_read =
  false` для всех новых строк, включая Sent);
- при повторной синхронизации (в т.ч. по `/mail/fetch/{connection}`) флаг
  `is_read` уже существующих в зеркале писем должен обновляться, если он
  изменился на сервере (например, письмо прочитали через веб);
- синхронизация должна замечать письма, исчезнувшие на IMAP-сервере
  (удалённые не через приложение), и удалять/помечать их как удалённые в
  зеркальной таблице — иначе они висят в приложении бессрочно.

## 6. Удаление письма в приложении не удаляет его на самом ящике

**Симптом:** пользователь удаляет письмо в приложении — оно пропадает из
списка в приложении, но продолжает быть видно в веб-версии почты (то есть
реально на IMAP-сервере). При этом клиент перед удалением показывает
предупреждение «Письмо будет удалено без возможности восстановления»
([mail_message_screen.dart:137-139](../lib/screens/mail_message_screen.dart#L137-L139)) —
то есть UX обещает необратимое удаление, а по факту (судя по симптому)
письмо не удаляется, а самое большее — скрывается в зеркальной таблице.

**Что вызывает клиент:** простой `GET /mail/delete/{connectionId}/{messageId}`
([mail_repository.dart:438-445](../lib/repositories/mail_repository.dart#L438-L445),
роут в [mail_routes.dart:68-69](../lib/config/routes/mail_routes.dart#L68-L69)),
без каких-либо параметров вроде `expunge`/`permanent`. Есть также пакетный
вариант `GET /mail/delete/few/{connectionId}`. По самой сигнатуре запроса
нельзя понять, что реально происходит на сервере.

**Нужно проверить на сервере:** выполняет ли обработчик этого роута настоящее
IMAP-удаление (`STORE \Deleted` + `EXPUNGE` на реальном ящике), или только
удаляет/помечает строку в локальной зеркальной таблице. Если только
зеркало — это не просто баг синхронизации, а функциональный баг: письмо
физически никогда не удаляется с сервера, хотя приложение утверждает
обратное.

## 7. Долгая загрузка детального экрана письма

**Симптом:** открытие письма (особенно непрочитанного) ощутимо медленнее,
чем список.

**Со стороны клиента:** [mail_message_screen.dart `_loadMessage()`](../lib/screens/mail_message_screen.dart#L52-L130)
при открытии письма делает один запрос
`GET /mail/get/message/{connectionId}/{messageId}`, и если письмо ещё не
прочитано — **последовательно**, вторым запросом (не параллельно),
`POST /mail/mark/read/{connectionId}/{messageId}`
([mail_message_screen.dart:83-106](../lib/screens/mail_message_screen.dart#L83-L106)).
Никакого лишнего клиентского перечитывания папки/тяжёлого синхронного
парсинга при открытии нет, вложения грузятся только по тапу пользователя —
то есть на клиенте это максимум «два последовательных round-trip вместо
одного» для непрочитанных писем, а не системная причина.

**Нужно проверить на сервере:**
- сколько реально занимает сам `GET /mail/get/message/...` — похоже, что он
  делает живой запрос к IMAP-серверу синхронно на каждое открытие письма
  (а не отдаёт из зеркальной таблицы, как список), это и есть вероятный
  источник задержки;
- можно ли отдавать тело письма сразу из зеркала (если оно там уже есть после
  синхронизации), обновляя его на фоне, а не блокировать открытие письма
  живым IMAP-запросом.
- как быстрый выигрыш на клиенте: можно сделать `mark/read` фоновым (не
  дожидаться его перед показом письма) — это уберёт один
  round-trip из критического пути, но не решит основную задержку, если она
  на стороне `get/message`.

## 8. Отправленные письма не появляются в папке «Отправленные»

**Симптом (2026-10-01):** письмо, отправленное из приложения, доходит до
получателя, но в «Отправленные» не попадает — ни в приложении (даже после
обновления), ни в веб-версии, ни в обычном почтовом клиенте этого ящика.

**Причина:** SMTP только доставляет письмо получателю, а копию в «Отправленные»
кладёт сам почтовый клиент отдельной командой IMAP `APPEND`. Gmail делает это
сам, корпоративные серверы (Exchange, Dovecot, Яндекс 360 и т.п.) — нет. Раз
письма нет даже в стороннем почтовом клиенте, бэкенд после отправки через
`/mail/smtp/send`, `/mail/smtp/reply/{email}` и `/mail/smtp/forward/{email}`
не делает `APPEND`. Клиент тут ничего исправить не может: он не знает ни
готового MIME письма, ни IMAP-доступа к ящику.

**Нужно:** после успешной отправки положить то же самое MIME-сообщение в папку
«Отправленные» того же подключения с флагом `\Seen`, затем обновить зеркало
этой папки (или сразу вставить строку письма в БД).

Набросок для Laravel + `webklex/php-imap` (подставить реальные имена):

```php
$sent = Mail::mailer($mailer)->send($mailable);          // Illuminate\Mail\SentMessage
$raw  = $sent->getSymfonySentMessage()->toString();       // полный MIME с заголовками

$client = $imapManager->make($connection->imapConfig());
$client->connect();
$folder = $this->findSentFolder($client)                  // SPECIAL-USE \Sent, иначе
    ?? $client->getFolderByPath('Sent');                  // по имени Sent/Отправленные/INBOX.Sent
$folder->appendMessage($raw, ['\Seen'], now());
```

- Папку искать по атрибуту SPECIAL-USE `\Sent`, а не по имени: у ящика бывает
  две «Отправленные» (`Sent` и `Отправленные`/`INBOX.Sent`), и письма видит
  только та, которую использует веб-интерфейс почты.
- Ошибка `APPEND` не должна ломать ответ отправки — письмо уже ушло. Её нужно
  залогировать, а клиенту вернуть `success: true`.
- Если в настройках подключения у SMTP-сервера включено автосохранение (Gmail),
  `APPEND` создаст дубль. Для `smtp.gmail.com` его нужно пропускать.

## 9. Вложения: у объекта вложения нет `id`, а встроенные картинки — без `content_id`

**Найдено на живом письме (2026-10-21):** в `GET /mail/get/message/{connection}/{email}`
вложения приходят без `id` (клиент получает 0) и без `Content-ID`. Клиент
строил ссылку на скачивание как `/mail/attachments/{connection}/{id вложения}/{filename}`,
т.е. `/…/0/image001.png` → 404. По api-docs второй сегмент — это `{email}`,
id **письма**. Клиент исправлен (передаёт id письма) — скачивание вложений
заработало.

Встроенные картинки (подписи Outlook, логотипы) в HTML ссылаются на
`src="cid:image001.png@01DD6160.0C8BDBF0"`. WebView такие ссылки открыть не
может, поэтому раньше вместо них были «?». Сейчас клиент сам находит вложение
по имени файла (часть `cid` до `@`), скачивает его и подставляет как data-URI.
Это работает для Outlook, но не для писем, где `cid` не совпадает с именем
файла (Gmail, Apple Mail: `cid:ii_lx2…`, `cid:F3A1…@apple.com`).

**Нужно:**
- В каждом объекте вложения отдавать `content_id` (значение заголовка
  `Content-ID` без `<>`) и `disposition` (`inline`/`attachment`). Клиент уже
  читает поля `content_id`/`contentId`/`cid` — после выкладки сопоставление
  по `cid` заработает для любых писем без доработки приложения.
- Желательно — отдавать `id` вложения или явно задокументировать, что
  `{email}` в маршруте скачивания — это id письма, а вложение определяется
  только по `{filename}`. Если в письме два вложения с одинаковым именем,
  скачать второе сейчас невозможно.
- Альтернатива (ещё лучше для клиента): заменять `cid:` прямо в `body_html`
  на URL `/mail/attachments/{connection}/{email}/{filename}`. Тогда картинкам
  нужна авторизация по токену в URL или cookie — WebView заголовок
  `Authorization` к картинкам не добавит.

## 10. Ответ и пересылка с вложениями

**Симптом:** если к ответу или пересылке прикрепить файл, письмо уходит как
новое: без `In-Reply-To`/`References` (у получателя не склеивается в цепочку),
а при пересылке — без вложений исходного письма.

**Почему:** `/mail/smtp/reply/{email}` и `/mail/smtp/forward/{email}`
принимают только JSON (`to`, `subject`, `body`), файлов в них передать нельзя.
Поэтому клиент с вложениями уходит через `/mail/smtp/send`.

**Нужно:**
- Принимать в `reply` и `forward` такой же `multipart/form-data`, как в
  `smtp/send`: поля `to`, `subject`, `body` и файлы `attachments[]`.
  Без файлов клиент по-прежнему шлёт JSON — оба формата должны работать.
- В `forward` прикладывать вложения исходного письма **и** новые файлы.
  Проверить заодно: прикладываются ли вложения исходного письма сейчас (без
  новых файлов) — по коду клиента это не видно.
- `to` может содержать несколько адресов через запятую
  (`Имя <a@x.ru>, b@y.ru`) — «Ответить всем» шлёт так всех участников.
  Разбирать список перед `Mail::to()` (см. также п. 11 про копию).

**После выкладки:** в клиенте поменять `MailRepository.replyAttachmentsSupported`
на `true` ([mail_repository.dart](../lib/repositories/mail_repository.dart)).
Отправка multipart в `reply`/`forward` уже написана, сейчас выключена этим
флагом; пока он `false`, в ответе и пересылке кнопка «Прикрепить файлы»
скрыта.

## 11. Получатели: весь список `to` и копия `cc`

Клиент раньше брал из `to` только первого получателя. Теперь он разбирает
`to` и `cc` как строку (`a@x, Имя <b@y>`), объект `{name, email}` или массив
таких объектов/строк, и показывает «Кому» и «Копия» в письме.

**Нужно:**
- Отдавать в письме (и в списке, и в `get/message`) всех получателей `to` и
  `cc`, а не только первого. Сейчас неизвестно, отдаёт ли сервер `cc` вообще —
  проверить на письме с копией.
- Для «Ответить всем» с копией: принимать в `smtp/send`/`reply`/`forward`
  отдельное поле `cc` (сейчас всех участников приходится класть в `to`).

## 12. Поиск

Поиск в списке писем теперь, помимо уже загруженных писем, ходит в
`GET /mail/search?q=…` и оставляет результаты текущего ящика.

**Нужно / проверить:**
- Параметр `connection_id` в `/mail/search` — сейчас поиск идёт по всем
  ящикам пользователя, и клиент отбрасывает чужие результаты постранично
  (страница может оказаться пустой).

Поиск по тексту письма не делаем: текст писем в базе не хранится (тело
читается с IMAP при открытии письма), искать серверу не по чему. Поиск
остаётся по теме и адресам.

## 13. `get/message` отдаёт IMAP UID вместо id письма

**Симптом:** ответ, пересылка и скачивание вложений падают с
`No query results for model [App\Modules\MailServices\Models\Email] 45969`.

**Почему:** `ImapService::getMessage()` возвращает `'id' => $message->getUid()`
— номер письма на IMAP-сервере, а не `emails.id`. Все остальные маршруты
(`reply/{email}`, `forward/{email}`, `attachments/{connection}/{email}/…`,
`mark/…`, `move/…`) ищут письмо по `emails.id` через route model binding, и
UID там не находится (или, хуже, находит чужое письмо с таким id).

**Клиент (2026-10-22):** после `get/message` подставляет id, по которому
письмо запрашивал, — ошибка ушла и без бэкенда.

**Нужно:**
- В `getMessage()` отдавать `'id' => $email->id`, UID — отдельным полем
  (`'uid' => $message->getUid()`), как `message_id` в `EmailResource`.
- Там же `'to' => $this->formatAddress($message->getTo()[0] ?? null)` берёт
  только первого получателя — отдавать `formatAddresses($message->getTo())`
  (см. п. 11).

## 14. Контракт `reply` / `forward`

Сверено с `ReplyEmailRequest`, `ForwardEmailRequest` и `SmtpController`.
Клиент с 2026-10-22 шлёт поля под сервер: ответ — `body_text`, пересылка —
`message` (раньше оба шли как `body` и сервер их молча отбрасывал — письмо
уходило без текста), пересылка нескольким адресатам — отдельным запросом на
каждого.

**Нужно / проверить на сервере:**
- **Ответ игнорирует `to` и `subject` клиента:** `replyToEmail` всегда шлёт
  на `$email->from['email']` с темой `'Re: ' . $email->subject`. Из-за этого
  не работает «Ответить всем» и правка получателей/темы. Брать `to`/`subject`
  из запроса (с фолбэком на исходное письмо) и разбирать список адресов.
- **Ответ на своё письмо** (из «Отправленных») уходит самому себе — то же
  `from['email']`.
- **Ответ без цитаты:** сервер не добавляет исходный текст в ответ, клиент
  кладёт цитату в `body_text` сам — так и оставить, либо договориться.
- **Пересылка:** `to` — `required|email`, то есть один адрес. Принимать
  список (или массив), чтобы не слать N отдельных писем.
- **Пересылка без вложений исходного письма:** `forwardEmail()` берёт из
  исходного только `from/date/subject/body_*`, файлы исходного письма не
  прикладываются.
- **`forward` возвращает `sendResponse(false)` при неудаче** — это
  `success: true, data: false`, клиент не видит ошибку. Отдавать `sendError`.
- **Файлы:** контроллер читает `$request->file('attachments')`, а правило
  `attachments.*.filename` (для base64-вложений) требует у каждого элемента
  `attachments` поле `filename` — multipart-файлы под `attachments[]` не
  пройдут валидацию. Развести ключи (например, файлы — `files[]`), см. п. 10.

## 15. `forward` падает с 500 «Server Error» на любом письме

`SmtpController::forwardEmail` и `SmtpService::buildForward*Body` вызывают
методы у значений, которые не являются объектами. Это PHP `Error`, а не
`Exception`, поэтому `catch (\Exception $e)` его не ловит и Laravel отдаёт
голый 500. Пересылка не работает ни для одного письма.

1. `ImapService::getMessage()` отдаёт `'date' => $message->getDate()->toString()`,
   то есть **строку**, а контроллер делает
   `$originalEmail['date']->format('Y-m-d H:i')`. Это первое падение.
2. `formatAddress()` отдаёт **массив** `['name' => …, 'email' => …]`, а
   `buildForwardBody()`/`buildForwardTextBody()` вызывают `$from->getName()` и
   `$from->getAddress()`. Это второе падение, сразу за первым.
3. Ящик берётся неправильно: IMAP читает через `getDefaultConnection()`
   вместо ящика самого письма, а SMTP-соединение для пересылки не выставляется
   вовсе. Если письмо лежит не в ящике по умолчанию, `getFolder()` ищет папку
   не на том сервере, и письмо уходит не с того адреса.

**Исправление:**

```php
// SmtpController::forwardEmail
$connection = isset($data['connection_id'])
    ? EmailConnection::query()->findOrFail($data['connection_id'])
    : $email->connection()->first();
$this->smtpService->setConnection($connection);
$originalEmail = (new ImapService())->setConnection($connection)->getMessage($email);

$originalEmailData = [
    'from'      => $originalEmail['from'],
    'date'      => \Carbon\Carbon::parse($originalEmail['date'])->format('Y-m-d H:i'),
    // …
];

// SmtpService::buildForwardBody / buildForwardTextBody
$fromName  = $from['name'] ?? '';
$fromEmail = $from['email'] ?? '';
// … htmlspecialchars($fromName) … htmlspecialchars($fromEmail) …
```

Плюс `catch (\Throwable $e)` вместо `\Exception` в контроллерах SMTP, чтобы
такие ошибки приходили клиенту текстом, а не голым 500.

**Клиент (с 2026-10-22):** пересылает через `/mail/smtp/send` с ящика письма,
исходное письмо идёт цитатой в `body_text` (без HTML и без вложений
исходного). Вложения к пересылке можно прикладывать. Когда `forward`
починят, можно вернуть `MailRepository.forwardMail` на `/mail/smtp/forward`
(передавать `message` без цитаты, сервер добавит её сам).

## 16. `smtp/send` теряет `connection_id` — письмо уходит с ящика по умолчанию

Клиент передаёт `connection_id`, `SendEmailRequest` его валидирует, но
`SmtpController::sendEmail` берёт значение из несуществующей переменной:

```php
$this->smtpService->sendEmail($request->validated(), $request->file('attachments'), $data['connection_id'] ?? null)
```

`$data` в методе не объявлена, `??` подавляет предупреждение, поэтому
`connectionId` всегда `null` и используется ящик по умолчанию. Из-за этого
клиент до сих пор вынужден переключать ящик по умолчанию перед отправкой
(п. 1).

**Исправление:**

```php
$data = $request->validated();
return $this->sendResponse(
    $this->smtpService->sendEmail($data, $request->file('attachments'), $data['connection_id'] ?? null)
);
```

После выкладки убрать из `MailRepository.sendMail` чтение `get/sendable` и
переключение `smtp/set` до и после отправки.

## 17. Безопасность: массовые операции без проверки владельца

`EmailController::massDelete` и `massMarkAsRead` берут письма по
`Email::whereIn('id', $request->input('emails'))` без `Gate::authorize` и
без проверки, что `{connection}` принадлежит текущему пользователю (в
отличие от `getByService`/`getByFolder`). Любой авторизованный пользователь
может передать чужие id писем и чужой `connection` — команды уйдут на чужой
IMAP-ящик с его учётными данными.

Там же `move`, `getMessage`, `markAsRead/Unread`, `delete`,
`downloadAttachment` проверяют только владельца письма, но не то, что письмо
относится к `{connection}` из URL.

**Нужно:**
- Во всех методах `EmailController` с `{connection}`: `Auth::id() === $connection->user_id`
  (или policy), иначе 403.
- В массовых методах — `->where('user_id', Auth::id())->where('connection_id', $connection->id)`
  и валидация `emails` как `required|array`, `emails.*` — `integer`.
- В одиночных — `$email->connection_id === $connection->id`.

## 18. Ошибки отдаются кодом 200, неудача IMAP — как `success: true`

`ApiBaseController::sendError` по умолчанию отвечает HTTP 200 с
`success: false`. А `ImapService::deleteMessage/moveMessage/markAsRead`
при исключении возвращают `false`, и контроллер отдаёт
`{"success": true, "data": false}` — неудача выглядит как успех.
`downloadAttachment` при ошибке тоже отдаёт 200 с JSON вместо файла.

Клиент с 2026-10-23 это обходит (проверяет `data == false`, а скачивание —
по `Content-Type: application/json` с `success: false`), но правильно:
- при неудаче IMAP-операции — `sendError` с текстом причины;
- `sendError` в этих местах с кодом 4xx/5xx, особенно для
  `downloadAttachment` — тогда любой клиент поймёт, что файла нет.

Для справки: `massMarkAsRead` читает список из `emails` — клиент слал `ids`,
из-за чего массовая отметка «прочитано» не работала (исправлено в клиенте
2026-10-23).
