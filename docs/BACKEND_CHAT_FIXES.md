# Чаты (`/api/chat/*`): что нужно от бэкенда

Найдено при ревизии раздела чатов в приложении (2026-10-23). Звонки — в
[BACKEND_CALLS.md](BACKEND_CALLS.md). Всё, что
можно было исправить на клиенте, уже исправлено; ниже то, что без бэкенда
не решается.

## 1. «Без звука» для чата — хранить на сервере

**Сейчас.** Флаг «Без звука» хранится только в телефоне. Приложение может
скрыть уведомление только на Android и только когда открыто. На iOS и на
Android в фоне уведомление показывает сама система, и до приложения оно
не доходит. Поэтому на практике «Без звука» почти не работает, а на другом
устройстве того же сотрудника не работает совсем.

**Нужно:**

- `POST /api/chat/{chat}/mute` и `POST /api/chat/{chat}/unmute` (или поле
  `is_muted` в `PATCH /api/chat/{chat}/members/{user}` для себя);
- `is_muted` текущего пользователя в ответах `GET /api/chat` и
  `GET /api/chat/{chat}`;
- при новом сообщении в замьюченный чат этому пользователю **не слать
  пуш** (или слать без `notification`, только `data`, чтобы обновить
  бейдж). Звонки (`type: CALL`) приходят всегда, даже если чат замьючен.

**Как проверить:** A мьютит чат с B, B пишет в чат. У A на iPhone и
Android (в фоне и с закрытым приложением) нет баннера и звука, а бейдж
непрочитанных при открытии растёт.
## 2. Реакции на сообщения

**Сейчас.** В приложении была панель реакций, но реакции видел только сам
пользователь, и при выходе из чата они пропадали. Мы её спрятали, чтобы
не вводить людей в заблуждение. В api-docs эндпоинтов для реакций в чате
нет, есть только для новостей (`/api/dashboard/news/reaction/{news}`).

**Нужно (по образцу новостей):**

- `POST /api/chat/{chat}/messages/{message}/reaction` с полем `emoji`:
  повторный вызов с тем же emoji снимает реакцию;
- в сообщении поле `reactions: [{emoji, count, me: bool}]`;
- событие Reverb в `chat.{id}`, например `MessageReactionUpdated` с
  `message_id` и `reactions`, чтобы реакция появлялась у собеседника сразу.

Набор emoji в приложении: ❤️ 👍 👎 😂 ‼️ ❓. Если на портале свой набор,
пришлите его, сделаем одинаковый.

## 3. События Reverb: один канал на пользователя

**Сейчас.** Приложение подписывается на `App.Models.User.{id}`,
`user.{id}` и **на отдельный `chat.{id}` для каждого чата**. Каждая
подписка — это отдельный `POST /broadcasting/auth`. У сотрудника с 200
чатами это 200+ запросов при запуске и после каждого обрыва сети.

**Вопрос:** приходят ли в канал пользователя (`App.Models.User.{id}`) все
события чатов этого пользователя: новое сообщение, правка, удаление,
прочтение, изменение состава? Если да, подписки на `chat.{id}` клиенту не
нужны, и мы их уберём. Если нет, предлагаем дублировать эти события в
канал пользователя: тогда клиенту хватит одного канала.

Ещё два события, которых сейчас нет совсем, поэтому клиент раз в 30 с
опрашивает сервер в открытом чате:

- закрепление и открепление сообщения (`MessagePinned` /
  `MessageUnpinned` с `message_id`);
- изменение названия, описания или аватара чата.

## 4. Окна редактирования и удаления — подтвердить

Клиент разрешает редактировать своё сообщение 15 минут, а удалять — 1 час
после отправки. Совпадает ли это с правилами сервера и портала? Если на
сервере ограничений нет или они другие, пришлите, какие именно: подправим
клиент.

## 5. Пересылка файлов (по желанию)

Чтобы переслать сообщение с файлом, клиент сейчас скачивает файл и заново
загружает его в целевой чат (`POST /api/chat/files`), потому что не знает,
пустит ли сервер участников целевого чата к файлу из чужого чата. Если
`POST /api/chat/{chat}/messages` с `forwarded_message_id` умеет сам
скопировать вложения исходного сообщения (с проверкой, что отправитель
видит исходный чат), напишите: тогда клиент перестанет гонять файлы через
телефон.

## 6. Ответ прямо из уведомления

Клиент добавил под пушем о новом сообщении кнопки «Ответить» (с полем
ввода) и «Прочитано». Ответ уходит обычным `POST /api/chat/{chat}/messages`,
потом `POST /api/chat/{chat}/read`. Новых эндпоинтов не нужно, нужно
поменять только формат пуша `type: chat_message`.

**iOS:** в APNs-часть пуша добавить категорию:

```php
'apns' => ['payload' => ['aps' => ['category' => 'CHAT_MESSAGE']]],
```

(в kreait/laravel-firebase: `ApnsConfig::fromArray([...])`). Без неё
iOS покажет обычный баннер без кнопок. В `data` по-прежнему нужен
`chat_id`.

**Android:** системное уведомление (пуш с блоком `notification`) кнопок
не умеет, поэтому для Android пуш о сообщении чата нужно слать как
**data-only**: без `notification`, с `android.priority = high`, а заголовок
и текст положить в `data`:

```php
'data' => [
    'type' => 'chat_message',
    'chat_id' => (string) $chat->id,
    'message_id' => (string) $message->id,
    'message_type' => $message->type,   // TEXT / STICKER / CALL …
    'title' => $title,                  // как сейчас в notification.title
    'body' => $body,                    // как сейчас в notification.body
],
'android' => ['priority' => 'high'],
```

Клиент сам нарисует уведомление с кнопками. Бонусом заработает «Без
звука» (п. 1) и на свёрнутом приложении: сейчас система показывает такие
пуши в обход клиента.

Для iOS блок `notification` оставить как есть, иначе баннер не появится
у выгруженного приложения.

## 7. Стикеры (`type: "STICKER"`)

Сообщения-стикеры уже могут приходить (`type: "STICKER"`, код стикера
в `message`/`content`). Картинок пока нет, приложение рисует заглушку.

- Пуш `chat_message` для стикера: `body` = `"Стикер"` (а не код), в data
  добавить `message_type: "STICKER"`. Фоновые баннеры iOS/Android
  показывает ОС по `notification.body` с сервера, клиент исправить их
  не может.
- То же для превью в вебе/портале и в любых текстах «последнее сообщение»,
  которые формирует сервер.
- Не валидировать код стикера по фиксированному списку `01…32`: набор будет
  расширяться.

Ещё: 01.10 отправка `type: STICKER` получала 422 (в правиле `in:` не было
`STICKER`). Проверить, что тип проходит валидацию.

**Проверка:** A отправляет стикер → пуш у B с текстом «Стикер», в списке
чатов «Стикер».
