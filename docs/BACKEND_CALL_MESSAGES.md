# Промт для Laravel-бэкенда: сообщения-звонки (`CALL`) и стикеры (`STICKER`) в чате

> Готовый промт для агента в репозитории Laravel-бэкенда. Сначала прочитай
> существующую реализацию: модели и контроллеры чата (сообщения, `chat__calls`),
> ring/accept/decline/end (см. `docs/BACKEND_CALLS.md` в мобильном репо),
> рассылку сообщений (Reverb/broadcast, вебхуки в Node, FCM/APNs). Предложи
> конкретный патч и только потом пиши код.

## Проблема

Звонок 1:1 не оставляет следа в чате. Мобильный клиент добавляет записи
«Начат звонок / Звонок завершён» только локально. Сортирует список чатов по
`created_at` последнего сообщения (и по `last_message_at`, если сервер его
отдаёт). Поэтому после любого `GET /chat` (возврат в приложение, реконнект)
чат, в котором только что был звонок, «съезжает» вниз. На других устройствах
и у собеседника звонка в ленте нет вовсе.

## Что сделать

### 1. Одно персистентное сообщение на звонок

- При создании звонка (`ring`, оба роута — публичный и internal) в той же
  транзакции, что и запись в `chat__calls`, создать сообщение в чате:
  - `type = "CALL"`, `sender_id = caller_user_id`, `chat_id` звонка;
  - `message` — короткий текст-фолбэк для старых клиентов и портала,
    например `"Звонок"`;
  - связь с звонком: колонка `call_id` в сообщениях (nullable, индекс)
    **или** `message_id` в `chat__calls`. Нужно, чтобы по звонку находить его
    сообщение без поиска по тексту.
- При каждом **финальном** статусе (`accepted` → потом `ended`, а также
  `declined`, `cancelled`, `missed`, `busy`, `failed`) **обновлять то же
  сообщение**, а не создавать новое. Сообщение должно получиться одно, даже
  если `end` пришёл с обоих устройств, от вебхука Prosody и по таймауту
  одновременно. Обновлять под той же блокировкой/условным `UPDATE`, что и
  статус звонка.
- Служебные статусы `answered_elsewhere` / `declined_elsewhere` сообщение
  не меняют.

### 2. Формат в API

Во всех местах, где отдаются сообщения (`GET /chat`, `messages`,
`GET /chat/{id}/messages`, ресурс сообщения в broadcast-событиях), для
`type == "CALL"` добавить объект `call`:

```json
{
  "id": 1234,
  "chat_id": 42,
  "sender_id": 7,
  "type": "CALL",
  "message": "Звонок",
  "created_at": "2026-10-19T12:00:00Z",
  "call_id": "c0ffee…",
  "call": {
    "id": "c0ffee…",
    "status": "ended",
    "duration": 75,
    "is_video": true,
    "started_at": "2026-10-19T12:00:05Z",
    "ended_at": "2026-10-19T12:01:20Z"
  }
}
```

- `status` — тот же словарь, что в `chat__calls` (`calling`, `ringing`,
  `accepted`, `declined`, `cancelled`, `missed`, `busy`, `ended`, `failed`).
- `duration` — секунды от `accepted` до `ended`; `null`/нет, если разговора
  не было.
- `created_at` сообщения = время начала вызова, его **не менять** при
  обновлении.

### 3. Последняя активность чата

- При создании сообщения `CALL` обновить у чата то же поле, что обновляется
  при обычном сообщении (`updated_at` / `last_message_at` / `last_message_id`),
  чтобы сортировка на сервере и в вебе тоже учитывала звонок.
- Если в ответе `GET /chat` ещё нет поля `last_message_at` — добавить
  (ISO-8601). Клиент берёт максимум из него и `created_at` последних сообщений.
- В `messages` (последние сообщения в списке чатов) сообщение `CALL` должно
  попадать наравне с остальными.

### 4. Рассылка

- Создание сообщения — тем же событием, что и обычное новое сообщение
  (Reverb `MessageSent`/аналог + вебхук в Node для портала). Клиент поднимает
  чат наверх сразу по этому событию.
- Обновление статуса/длительности — событием обновления сообщения
  (`MessageUpdated`/аналог). Клиент не помечает такие сообщения «изменено».
- **Не** отправлять обычный пуш `chat_message` о сообщении `CALL`: у звонка
  свои пуши (`chat_call`, `chat_call_ended`…). Если не отправлять сложно,
  добавьте в data `message_type: "CALL"`, и приложение не покажет баннер.

### 5. Непрочитанные

- Для собеседника (не звонящего) сообщение `CALL` со статусом `missed`
  считать непрочитанным (обычный `statuses[].read = false`). Пропущенный
  звонок поднимает бейдж, как в мессенджерах.
- Остальные статусы можно сразу помечать прочитанными для обоих участников
  — на усмотрение, клиент поддерживает оба варианта.

### 6. Ограничения

- Сообщение `CALL` нельзя редактировать (`PATCH` → 422) и пересылать.
  Удалять — по тем же правилам, что обычные сообщения.
- Групповые звонки (ссылка на видеовстречу) не трогать — это отдельный
  механизм через текстовое сообщение-приглашение.

## Стикеры (`type: "STICKER"`)

Сообщения-стикеры уже могут приходить (`type: "STICKER"`, код стикера
в `message`/`content`). Картинок пока нет, приложение рисует заглушку.

- Пуш `chat_message` для стикера: `body` = `"Стикер"` (а не код), в data
  добавить `message_type: "STICKER"`. Фоновые баннеры iOS/Android
  показывает ОС по `notification.body` с сервера, клиент исправить их
  не может.
- То же для превью в вебе/портале и в любых текстах «последнее сообщение»,
  которые формирует сервер.
- Не валидировать код стикера по фиксированному списку `01…32`: набор будет
  расширяться.

## Совместимость

- Старые версии приложения увидят `CALL` как текст `message` («Звонок») —
  поэтому фолбэк-текст обязателен.
- Новое приложение со старым бэкендом работает как раньше (локальные
  записи о звонке). Как только сервер присылает `CALL` с тем же `call_id`,
  локальные записи заменяются серверной.

## Проверка

1. Звонок A→B, разговор 1 мин. В ленте у A «Исходящий звонок · 01:00»,
   у B «Входящий звонок · 01:00». Чат наверху у обоих. Свернуть/развернуть
   приложение (полный `GET /chat`) — чат остаётся наверху.
2. A звонит, B не отвечает → одно сообщение, у B «Пропущенный звонок»
   и +1 к непрочитанным, у A «Нет ответа».
3. `end` одновременно с двух устройств + вебхук Prosody → одно сообщение,
   длительность одна.
4. A отправляет стикер → пуш у B с текстом «Стикер», в списке чатов «Стикер».
