## Пояснения к пунктам

### Пп. 1–3. Чужой профиль, бронь, уведомления: только прямыми запросами

В интерфейсе приложения и, скорее всего, портала таких кнопок нет. Это не
значит, что проблемы нет: сервер не проверяет, чей id пришёл в запросе.
Любой сотрудник может взять свой токен (из приложения или из инструментов
разработчика в браузере на портале) и отправить запрос через Postman или
curl, подставив чужой id. Id видны в ответах сервера, например в списке
сотрудников. Исправить можно только на сервере.

**Как проверить** на тестовом сервере с двумя пользователями A и B. Меняйте
безобидное поле:

```bash
curl -X POST "https://<сервер>/api/user/update/<id_B>" \
  -H "Authorization: Bearer <токен_A>" \
  -H "Accept: application/json" \
  -F "theme=dark"
```

Ошибка (403, 404 или `success: false`) — защита есть, пункт вычеркнуть.
`success: true` и у B сменилась тема — дыра на месте. Так же можно было бы
поменять e-mail, телефон или отключить аккаунт.

Быстрее, чем запросом: открыть `UserService::update()` и посмотреть, есть ли
в начале условие «меняет себя или админ». Тем же способом проверяются п. 2
(`POST /booking/update/{id}`, токен участника, не организатора) и п. 3
(`POST /user/notifications/delete/{id}` с номером чужого уведомления).

**П. 1.** Кроме проверки владельца: поле `is_active` менять может только
админ.

**П. 2.** Здесь две разные проблемы.

1. *Чужая бронь* — только прямым запросом или из старой версии приложения:
   в новой версии кнопки «Изменить» и «Удалить» видят только создатель и
   организатор.
2. *Двойное бронирование при переносе* — возможно и штатно. При создании
   сервер проверяет, свободен ли объект, при переносе (`update`) — нет.
   Приложение это обходит: переносить можно только встречи без
   переговорной, места или парковки. Но если портал позволяет перенести
   бронь переговорной, там обычный пользователь займёт уже занятое время.
   Проверить: перенести на портале бронь переговорной на время чужой брони.
   После исправления приложение откроет перенос переговорных (п. 40).

**П. 3.** Чужое уведомление нельзя прочитать — только пометить прочитанным
или удалить, перебирая номера (они идут подряд). Утечки нет, но человек не
узнает, что ему что-то приходило. Вторая половина пункта — скорость, не
безопасность: ради числа на бейдже `unread()` выгружает все непрочитанные,
а приложение запрашивает счётчик на каждый пуш и при каждом возврате в
приложение.

### П. 4. Адреса без авторизации

Только сервер, приложение эти адреса не вызывает. В отличие от пп. 1–3, здесь
не нужен даже токен: запрос может отправить кто угодно из интернета.

1. **`POST /documents/notifications` — самое важное.** Через него 1С сообщает
   серверу о новом документе на согласование, сервер рассылает пуш. Ни ключа,
   ни подписи нет: зная guid сотрудника, можно отправить фальшивое «документ
   на согласование» хоть директору, от имени нашей системы. На неизвестный
   guid сервер отвечает отдельной ошибкой (404 «не обнаружено ни одного
   пользователя с такими guid»), так что существующие guid можно перебрать.
   - Защитить общим секретом в заголовке, как Jitsi-вебхук
     (`VerifyJitsiWebhookToken`), значение — в конфиге на каждый
     `documents_service`.
   - Если 1С не умеет заголовки — пускать только с IP сервера 1С на nginx.
     Если такое ограничение уже стоит, достаточно подтвердить: из кода это не
     видно.
   - На неизвестный guid отвечать так же, как на успех (200, `data: false`).
2. **`GET /test/mail` — забытый тестовый адрес.** Любое открытие в браузере
   отправляет письмо пользователю с id 8; тысяча открытий — тысяча писем.
   Удалить или оставить только при `APP_ENV=local`.
3. **`POST /auth/user/{id}` — мусор.** Ведёт на
   `AuthController::authenticate`, которого нет, поэтому всегда отвечает
   ошибкой 500. Вреда нет, удалить.

Проверено по копии кода от сентября 2026. Если на проде этих адресов нет или
они уже закрыты, пункт можно вычеркнуть.

### П. 6. Пуши после выхода из аккаунта

**Симптом.** Человек вышел из аккаунта, а на телефон продолжают приходить
пуши и VoIP-звонки (iOS). Если на этом телефоне потом вошёл другой
сотрудник, он может получать уведомления предыдущего.

**Что делает приложение** (с 01.10.2026). При выходе по порядку:
`POST /devices/fcm/delete` (FCM-токен), `POST /devices/voip/delete`
(VoIP-токен iOS), `/auth/logout`, затем удаляет токен FCM на телефоне и
отключает PushKit. VoIP-пуш, пришедший без входа, сразу сбрасывается.

**Чего не хватает на сервере:**

1. Маршрута `POST /devices/voip/delete` нет — приложение получает 404, и
   VoIP-токен остаётся в `voip_device_tokens`. Добавить по образцу удаления
   FCM-токена.
2. `/auth/logout` должен сам удалять FCM- и VoIP-токены, привязанные к этой
   сессии (`currentAccessToken()->id`): если приложение не успело вызвать
   удаление (нет сети, приложение убили), токены всё равно не должны жить.
3. Регистрация токена — уникальный upsert по самому токену: если такой токен
   уже есть у другого пользователя, перепривязать его к новому, а не
   добавить вторую строку.
4. Если FCM ответил `UNREGISTERED` или 404/410 — удалять токен из базы.

**Проверка.** Войти под A, выйти, войти под B на том же телефоне. Написать
A в чат и позвонить A — на телефоне не должно быть ни баннера, ни звонка.
В таблицах токенов у A не осталось строк этого устройства.

### П. 14. Push о новых письмах перестали приходить

Раньше push о новом письме точно приходил, потом перестал. Описание в MAIL §4
написано в сентябре по жалобе и чтению кода, по логам не проверялось.

**Приложение, скорее всего, ни при чём.** Пуш с блоком `notification` в фоне
показывает сама система, приложение не может его ни скрыть, ни потерять.
Код приёма (`type` = `mail` или `email`) с 28.09 не менялся по сути. Подписки
на темы FCM восстанавливаются при входе и запуске.

**В сентябрьской копии `laravel-core-dev` пуш о письме никто не отправляет:**

- `UserNotificationService::createEmailNotification()` (тип `email`) есть,
  но нигде не вызывается;
- `FetchService::createNewEmail()` и `ImapService::createNewEmail()`
  сохраняют письмо без уведомления;
- общий механизм такой: создание записи `UserNotification` →
  `UserNotificationObserver` → очередь `SendUserNotificationPush` →
  `PushNotificationService::notifyUserNotification()`.

Значит, на проде этот пуш шлёт либо код новее сентябрьской копии, либо
другой сервер (Node, портал).

**Что проверить:**

1. Кто на проде отправляет пуш о письме и вызывается ли он сейчас.
2. Работает ли воркер очереди. `SendUserNotificationPush` — job в очереди:
   если воркер упал, перестают приходить все пуши из `user_notifications`
   (новости, документы, опросы), не только почта. Если пуши о документах
   приходят, а о письмах нет, дело не в очереди.
3. Работает ли планировщик синхронизации почты: если новые письма не
   подтягиваются с IMAP, пушить нечего.
4. В логе прода после тестового письма: `FCM push finished` /
   `FCM push skipped` / `FCM send failed`.

**Проверка.** Отправить письмо на ящик, подключённый в приложении, закрыть
приложение, подождать интервал синхронизации. Должен прийти баннер, тап
открывает письмо.

### П. 15. Прочтение и удаление не доходят до почтового ящика

**Проверено 26.10.2026 на реальном ящике (Outlook):** письмо открыто в
приложении — в Outlook осталось непрочитанным; письмо удалено в приложении —
в Outlook осталось на месте. Отправка работает. Приложение вызывает
правильные маршруты: `POST /mail/mark/read/{connection}/{email}`,
`GET /mail/delete/{connection}/{email}`.

**Главная причина (сентябрьская копия `laravel-core-dev`).** В
`emails.message_id` хранится IMAP UID (`EmailService.php:48`), а письмо
ищется только по `message_id` + `connection_id`, без папки:
`ImapService::processMessage()`, `createNewEmail()`, `EmailService.php:80`.
В миграции `emails` нет уникального индекса, папка в ключ не входит.

UID по стандарту IMAP уникален **только внутри одной папки**: у письма во
«Входящих» и у письма в «Отправленных» UID легко совпадают (в Exchange UID в
каждой папке идут с 1). Тогда в зеркале остаётся одна запись на два письма,
а `updateExistingEmail()` при синхронизации следующей папки переписывает ей
`folder_id`. После этого `markAsRead()` / `deleteMessage()` берут
`$email->folder` и UID и ставят `\Seen` или переносят в корзину **другое
письмо** из другой папки, а нужное не трогают. Это не только «не работает»,
но и риск потери данных: в корзину может уйти не то письмо.

**Ещё три проблемы рядом:**

1. `ImapClientFactory` включает `options.soft_fail = true`: если письмо по UID
   не найдено, `getMessage()` не бросает исключение, а `markAsUnread()` и
   `deleteMessage()` не смотрят на результат `setFlag()` / `move()` и
   возвращают `true` — приложение считает, что всё получилось.
2. `deleteMessage()` переносит через `move($path, false, true)`: второй
   аргумент — `expunge = false`. Если сервер не поддерживает `MOVE`, библиотека
   делает COPY + `\Deleted` без EXPUNGE, и письмо остаётся в исходной папке.
   Без корзины ставится только `\Deleted`, тоже без EXPUNGE.
3. Синхронизация (`getDateRangeForFolder()`) забирает письма начиная с даты
   последнего письма минус сутки. Поэтому статус, изменённый в Outlook, и
   удаление в веб-почте доходят до приложения только для писем за последние
   сутки; `markMissingEmailsAsDeleted()` видит тоже только это окно.

**Сделать:**

1. Во всех поисках письма добавить `folder_id`; уникальный индекс
   (`connection_id`, `folder_id`, `message_id`). Миграцией убрать «склеенные»
   записи и пересинхронизировать ящики. Хорошо бы хранить и `UIDVALIDITY`
   папки: при его смене старые UID недействительны.
2. В `markAsRead` / `markAsUnread` / `deleteMessage` / `moveMessage` проверять,
   что письмо на IMAP найдено (UID, лучше и заголовок `Message-ID`) и что
   `setFlag()` / `move()` вернули успех. Иначе `sendError` с причиной —
   приложение покажет ошибку и вернёт письму прежний статус.
3. При удалении — `move($path, true)` (с expunge) или явный EXPUNGE после
   `\Deleted`.
4. Флаги: отдельным лёгким запросом `UID FETCH 1:* (FLAGS)` обновлять
   `is_seen` и находить пропавшие письма хотя бы за 30 дней, а не за сутки.

**Что посмотреть в логах прода** (канал `MailServices`): «Ошибка отметки
письма как прочитанного», «Ошибка удаления письма». Если ошибок нет, а
статус не меняется, — это совпадение UID (не то письмо) или `soft_fail`.

**Проверка.** Во «Входящих» и «Отправленных» есть письма с одинаковым UID.
Открыть входящее в приложении → в Outlook оно прочитано, отправленное с тем
же UID не изменилось. Удалить входящее → оно в «Удалённых», в исходной папке
его нет. Прочитать в Outlook письмо недельной давности → после обновления в
приложении точки нет.

### П. 27. Дубли сообщений в чате

`ChatService::sendMessage()` (`app/Modules/Chats/Services/ChatService.php`)
всегда делает `Message::query()->create([...])`: нет ни ключа от клиента, ни
проверки дублей. Если ответ на `POST /chat/{id}/messages` потерялся в сети и
запрос повторился, в чате появляется два одинаковых сообщения. В приложении
двойное нажатие уже исключено, остаётся только сетевой повтор.

**Сделать:**

1. Принимать в `SendMessageRequest` необязательное поле `client_id` (UUID,
   генерирует приложение).
2. Перед созданием искать сообщение с тем же `chat_id` + `sender_id` +
   `client_id`. Нашлось — вернуть его, как будто оно только что создано, без
   повторной рассылки и пуша.
3. Колонка `client_id` (nullable) и уникальный индекс
   (`chat_id`, `sender_id`, `client_id`). Старые клиенты без поля работают
   как раньше.

Как будет готово, напишите — приложение начнёт отправлять `client_id`.

### Пп. 33–37. Старые патчи: проверить, что они на проде

Эти исправления передавались текстом или делались в локальной копии
`laravel-core-dev`, которая не под git. Попали ли они на прод, мы не знаем.

**П. 33. Пересылка сообщения.** Было: приложение отправляет
`forwarded_message_id`, а сервер его отбрасывает (нет ни в
`SendMessageRequest`, ни в базе), и пересланное выглядит как обычное
сообщение. Патч: миграция с колонкой `forwarded_message_id`, связи в модели
`Message`, валидация в `SendMessageRequest`, поле в `MessageResource`,
сохранение в `ChatService::sendMessage()`.
Проверка: переслать сообщение из приложения, открыть чат на портале или
заново в приложении — должна остаться пометка «Переслано от …».

**П. 34. Удаление сообщения.** Портал удаляет через Node-сервер чатов: текст
заменяется на «Сообщение удалено», строка остаётся. Приложение удаляет через
Laravel (`/mobile/api/chat/{chat}/messages/{msg}/delete`), а
`ChatService::deleteMessage()` делает `$message->delete()` — строка
пропадает совсем, у собеседника сообщение просто исчезает. Патч: в
`deleteMessage()` делать то же, что Node — записать текст «Сообщение
удалено» через `prepareMessageStorage('Сообщение удалено', 'TEXT')`,
`type = TEXT`, удалить `MessageFile` и закрепление, строку оставить,
разослать событие удаления.
Проверка: удалить сообщение из приложения — у собеседника в приложении и на
портале на его месте «Сообщение удалено».

**П. 35. Код подписи на почту.** `DocumentsServiceService::checkRight()`
вызывает `generateCode()`, если у пользователя нет `user_authorised:{email}`.
Любой запрос к сервису подписи (например, фоновое обновление счётчика) без
действий человека отправлял ему на почту код. Приложение с 01.10.2026 эти
запросы не делает, но любой другой клиент вызовет то же самое. Патч: убрать
`generateCode()` из `checkRight()` — код отправлять только по явному
запросу входа в сервис подписи.
Проверка: открыть «Согласования», не входя в сервис подписи, подождать
10 минут — письма с кодом быть не должно.

**П. 36. Прикрепление файла в чате.** `ChatFileService::store()` считал
SHA-256 (64 символа), а колонка `chat__files_hash.file_hash` на проде —
32 символа. Вставка падала внутри транзакции, файл не сохранялся, сообщение
не уходило. Исправление: `hash_file('md5', ...)` (ровно 32 символа),
миграция в коде поправлена под 32. Это правка кода, миграция на проде не
нужна. Проверка: прикрепить файл в чате из приложения — сообщение с файлом
дошло.

**П. 37. Пуш чата.** В `ChatService::sendMessage()` `broadcast()` вызывался
внутри транзакции до регистрации `DB::afterCommit(...)` для пуша: если
Reverb недоступен, исключение откатывало транзакцию, и пуш не отправлялся.
Исправление: `afterCommit` до `broadcast()`, а `broadcast()` в try/catch с
`report()`. Ещё добавлен лог «нет токенов» в `notifyChatCallRing()`.
Проверка: отправить сообщение и найти в логе прода `FCM push finished` /
`FCM push skipped` / `FCM send failed` с `type=chat_message`.
